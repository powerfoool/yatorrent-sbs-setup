# Координатор на отдельной машине

## Настройка

Используй общую установку из SKILL.md: YaTorrent, внешний AIM2, private Codex/Node, Playwright/Chromium, exact rules, native executor-runtime.json, 11слотов, timeout1800, concurrency4. По умолчанию эта машина принимает Codex tasks наряду с ролью координатора. Не рассчитывай на файлы/авторизацию/утилиты других Mac. Поручение только собрать пакет не запускает эту настройку.

Дополнение `python3 scripts/coordinator_setup.py --plan` не меняет систему. `--apply --root ROOT` требует готовый общий runtime, ставит private JSON Schema2020-12 validator (закреплённые зависимости в отдельном Python venv), gws через Homebrew при отсутствии и private root/bin/gwsx. Этот standalone wrapper поддерживает `work`, `status work`, Sheets/auth/schema; сохранённые credentials лежат в вычисленной ~/.config/gws-corp-app либо --google-config владельца. Он не заменяет чужой глобальный launcher и не читает токены через LLM. Используй `export PATH=ROOT/bin:$PATH` в сессии координатора либо полный путь; не подставляй root автора.

Python≥3.10 проверяется до изменений; ранее созданный несовместимый coordinator venv сохраняется в backups и пересоздаётся выбранным supported Python. Wrapper и auth status запускают gws с cwd=/ и отклоняют существующий /.env, чтобы dotenv проекта/предков не мог вернуть чужой токен после очистки env. Файловые аргументы gws при необходимости передавай абсолютными путями.

Авторизация отдельная от Codex/AIM2. По умолчанию Sheets scope read/write: https://www.googleapis.com/auth/spreadsheets. Ни Drive, ни Gmail для обычной таблицы не требуются. Если вход уже доступен, проверь его и конкретную таблицу, не заставляй пользователя повторять OAuth без причины. gws auth status новых версий не показывает scopes: неизвестный write scope не считать подтверждённым. OAuth client Desktop предоставляет владелец вне ZIP: его локальный файл копируется в `<google-config>/client_secret.json` (по умолчанию ~/.config/gws-corp-app/client_secret.json), с правами0600; каталог0700. Не путать этот каталог с дефолтным ~/.config/gws из общего руководства. [официальная настройка Google CLI](https://github.com/googleworkspace/cli#authentication). Владелец завершает Google consent на этом Mac. Команда `gwsx work --confirm auth login --scopes https://www.googleapis.com/auth/spreadsheets`. Не копируй вход автора/другого аккаунта. При отсутствии клиента объясни, зачем нужен этот файл, и предложи использовать корпоративный Desktop client или создать собственный в Google Cloud.

`coordinator_setup` возвращает awaiting_google_login/ненулевой код, если вход недоступен. Успех означает только local tools/auth; не доказывает доступ к выбранному документу, запись, свежий worker или broker end-to-end. Для файловых входов/выходов --no-google пропускает Google; формат результатов согласуется всё равно.

## Понятный разговор и согласование

Считай пользователя новичком. Спрашивай о результате, не реализации. При первом запуске объясни одним предложением, что координатор прочитает пары, поручит сравнение исполнителям и вернёт оценки. Если список уже дан, не проси его повторно. Прежде чем разметить, прочитай метаданные листа и необходимые заголовки/строки.

Предложи компактный выбор и возможность собственного варианта:
1. Рекомендуемый при существующих колонках: «Итог в колонке оценки, подробный разбор в комментарии». JSON объясни как структурированный текст с полями, не требуй от пользователя знания формата.
2. «Отдельные колонки для итоговой оценки, качества левой/правой выдачи и причин выбора». Покажи будущие заголовки, образец строки, куда уйдёт полный разбор.
3. «Отдельный файл с результатами, таблицу не менять».

Согласуй словарь вердиктов (например левая/правая/равны/недостаточно данных), оценочную шкалу рубрики, причины победителя, URL/аспекты в подробностях, ошибку/неизвестные поля. Не навязывай новую шкалу вместо промпта пользователя. Предложение изменить структуру таблицы покажи конкретно: новые поля и точные диапазоны, существующие данные сохранить. Пользователь выбирает; уже согласованная запись каждой завершённой строки не требует нового подтверждения.

В private agreement.json сохрани schema_version1, approved=true **только после реального выбора владельца**, approval_note с его решением, spreadsheet_id/sheet_id/sheet_title, input_columns, outputs (колонка→JSON Pointer либо явно согласованная пустота), output_schema, projection при адаптере, overwrite policy/ошибки. На resume используй тот же формат; изменение результата согласуй. Не представляй автоматически созданное approved=true как пользовательское согласие. Технический result_pool выбирает координатор: сохранённый agreement.result_pool имеет приоритет, известный config.result_pool можно передать через `prepare --broker-config PRIVATE_CONFIG.json`; иначе helper выбирает kron. Это небольшая настройка помощника с ключом result_pool, не обещание такого поля в AIM2. Не угадывай неизвестную схему AIM2 и не передавай туда credentials ради выбора pool. Сохрани выбранный pool в private плане до публикации и используй его при получении; пользователя об именах pool не спрашивай.

Пример **варианта для согласования**, не универсальные колонки:
```json
{
 "schema_version":1,"approved":false,"approval_note":"",
 "spreadsheet_id":"OWNER_DOCUMENT_ID","sheet_id":0,"sheet_title":"Фактическое имя листа",
 "input_columns":{"id":"A","query":"B","left_html":"G","right_html":"H"},
 "outputs":{"P":"/winner","V":""},
 "output_schema":{"type":"object","properties":{"winner":{"type":"string"},"winner_reason":{"type":"string"}},"required":["winner","winner_reason"],"additionalProperties":false}
}
```
Без адаптера outputs в helper — колонка→JSON Pointer к **output_schema**: пустая строка означает весь JSON. Для декомпозиции можно сопоставить /left_score, /right_score, /winner_reason и другие **реальные объявленные** поля схемы. Локальные $ref и индексы массивов поддержаны; удалённые ссылки нужно заранее разрешить локально. Необъявленные пути отклоняются до подготовки задания, даже если additionalProperties не запрещены. Предложенная схема должна содержать весь согласованный разбор бригадира, а не только краткий пример. Объект `{"literal":null}` вместо Pointer означает явно согласованную пустую ячейку. Это не поле уверенности/качества и не попытка его вычислить.

## Переход сохранённого формата на URL-only r9

Сохранённый approved agreement прежнего стандартного r7/r8 формата нельзя использовать вслепую: его output_schema может требовать integer для extra_blocks.score и ровно пять URL, тогда как V2 требует null для extra_blocks.score и допускает0–5 URL. Фактическая прямая команда владельца перейти на URL-only контракт разрешает координатору обновить прежнюю стандартную output_schema из schemas/default-final.schema.json и записать эту команду в receipt; destination, колонки, projection и overwrite policy сохраняются. Затем заново выполни validate для схемы/mapping и project для примеров завершённого и inconclusive ответа до отправки. Это сопровождает уже описанную замену старых стандартных HTML-ожидающих ролей текущими V2 defaults.

Пользовательскую output_schema не переписывай молча. Если она несовместима с V2, покажи конкретное различие простыми словами и согласуй формат до отправки, сохранив независимую подготовку. extra_blocks.score=null означает «визуальная выдача и дополнительные блоки не переданы и не оценены», а не низкую оценку или недоступный сайт. Null отдельного URL-аспекта означает недостаток доказательств именно этого аспекта; окончательные left_score/right_score/winner=null означают материальную неизвестность, способную изменить SBS. Подтверждённая пустая органическая сторона и extra_blocks=null сами по себе не требуют inconclusive.

### Готовая проекция стандартного ответа в Q–W

Если владелец выбрал Q–W и разрешил пустые R/V, скопируй **полную** `schemas/default-final.schema.json` в output_schema agreement, добавь следующие поля. Это исполняемый offline адаптер, исходная worker schema остаётся восьмиполевой:
```json
{
 "projection":{"adapter":"standard-qw-v1"},
 "outputs":{"Q":"/status","R":{"literal":null},"S":"/winner_label","T":"/left_score","U":"/right_score","V":{"literal":null},"W":"/comment"}
}
```
Под адаптером Pointer проверяется относительно отдельной projection_schema: status (done/inconclusive), winner_label (строка), left_score/right_score (integer/null), comment (строка); эти пять полей обязательны, additionalProperties=false. Helper предоставляет эту фиксированную схему как `coordinator_data.QW_SCHEMA`; необязательная projection_schema в agreement должна совпадать с ней. output_schema всегда относится к ответу worker, именно она отправляется в задаче и проверяется JSON Schema validator. Не добавляй /status, /confidence, /broken, /translated_winner или /comment в mapping стандартного ответа без адаптера: таких полей нет.

extra_blocks.score=null — штатная исключённая область URL-only оценки, не причина inconclusive для адаптера. При двух integer оценках1–5 и winner left/right/tie Q=done; S=Yandex Old/Yandex New/Ничья, T/U — целые числа. Если хотя бы одна оценка или winner=null, Q=inconclusive, S/T/U пусты. R/V всегда пусты по этому согласованному mapping. W содержит winner_reason, перевод строки и **полный** исходный JSON в детерминированной компактной сериализации; исходные частичные оценки сохраняются там. Адаптер не придумывает уверенность, качество или признак поломки; неподходящий winner/тип оценки отклоняется. >49000символов в W отклоняется без усечения, требуется согласованный другой формат.

Пример завершённой строки: `done | пусто | Yandex Old | 5 | 3 | пусто | причина + полный JSON`. Пример недостаточных данных: `inconclusive | пусто | пусто | пусто | пусто | пусто | причина + полный JSON`.

До публикации выполни две отдельные проверки и прогон двух примеров:
```text
ROOT/bin/coordinator-validate RUN/agreement.json
python3 scripts/coordinator_data.py validate --agreement RUN/agreement.json --output RUN/mapping-preflight.json
ROOT/bin/coordinator-validate RUN/agreement.json RUN/example-completed.json
python3 scripts/coordinator_data.py project --agreement RUN/agreement.json --input RUN/example-completed.json --row 3 --output RUN/example-completed-cells.json
ROOT/bin/coordinator-validate RUN/agreement.json RUN/example-inconclusive.json
python3 scripts/coordinator_data.py project --agreement RUN/agreement.json --input RUN/example-inconclusive.json --row 3 --output RUN/example-inconclusive-cells.json
```
Проверь Q–W, integer/пустые значения, RAW и длину W. Эти команды не отправляют задания и не записывают таблицу. Успех `schema_valid=true` проверяет только worker schema/answer; mapping-preflight проверяет объявленные пути и адаптер отдельно. `prepare` повторяет проверку mapping перед созданием envelope.

## Чтение входов

`gwsx work sheets spreadsheets get --params '{"spreadsheetId":"ID","fields":"spreadsheetId,sheets.properties"}'`

Разреши gid в фактическое имя листа: это не всегда Sheet1. Values get для точного диапазона, JSON argument передай как отдельный argv (не shell string с данными):
`gwsx work sheets spreadsheets values get --params '{"spreadsheetId":"ID","range":"Фактический лист!A1:V20"}'`

На координаторе прочитай query, region/device, исходные HTML либо готовые top5 и устойчивый source ID. Локально извлеки органический top-5; проверь рекламу и tracking-ссылки по реальным карточкам, не по одному имени класса. Передай pair с id/query, необязательными region/device и left_top5/right_top5 — до пяти объектов {position,url} на каждой стороне, позиции1–N подряд в исходном порядке. Дубли сохраняются. Для короткой выдачи передай фактическое число подтверждённых результатов, без дополнения или выдуманных URL. [] допустим только при распознанной пустой выдаче (например EmptySearchResults без органических ссылок) либо явно предоставленном проверенном пустом ranking. Неизвестный формат, потерянный HTML или ошибка парсера — ошибка входа до публикации, а не пустой ranking. Доказательства извлечения сохраняй в private журнале координатора; в wire передай только0–5 URL/позиций. Относительный адрес разрешай только по фактическому base/source URL на координаторе; этот source URL исполнителям не передавай. HTML, titles, snippets, изображения и source SERP URL не входят в pair, PromptItem prompt или тексты выбранных ролей. Скрипт prepare принимает уже извлечённую URL-only pair; HTML-разбор выполняет координатор до него. Существующие человеческие/старые оценки не передавай бригадиру. Если ID нет, согласуй стабильную идентификацию и не используй один номер строки: сортировка меняет его. Для идентичных дублей нужен отдельный согласованный ID. Локальный HTML-источник не обрезай молча: пустое/усечённое/ссылка вместо HTML требует отдельного чтения и проверки исходника. Это локальная проверка координатора, а не разрешение отправить HTML worker. input_columns могут ссылаться на локальные HTML-колонки: это конфигурация чтения координатора, не поля wire pair. Снимок исходников, подтверждение короткой/пустой выдачи и URL-only hash сохраняются локально; неизвестные важные поля уточни понятным вопросом.

## Задания и прогресс

Стандартные роли находятся в `prompts/foreman.md` и `prompts/scout.md` **в этом навыке**. Их читает только координатор. Полные тексты уже самодостаточны: критерии, шкала, структура результата разведчика/бригадира и ограниченный обход. Бригадир и разведчик получают текст в input_data и никаких файлов навыка не читают. Не передавай workers ссылку на архив для загрузки правил. Дополнительные rubrics/metadata не должны вводить чтение assessment files.

Для первого запуска объясни стандартный результат простыми словами: «Рекомендую три оценки посещённых страниц, четыре оценки ранжирования top-5, общий балл и причину выбора по шкале1–5. Внешний вид выдачи недоступен: сохранённый extra_blocks получает null. Можно изменить правила или формат». Стандартная JSON Schema — `schemas/default-final.schema.json`, читает её координатор и включает в согласованную output_schema. Выбор удобных колонок не требует менять полную схему разбора: helper извлекает нужные поля JSON Pointer либо применяет согласованный standard-qw-v1. Формат записи согласовать по разделу выше. Команда начать разметку с этим навыком разрешает первичное применение стандартных инструкций; отдельное требование принести файлы или повторно подтвердить запуск отсутствует.

Фиксация стандартного выбора и подготовка одного задания:
```text
python3 scripts/coordinator_prompts.py --state RUN/instructions.json --user-command 'Фактическая команда пользователя начать разметку с этим навыком'
python3 scripts/coordinator_data.py prepare --agreement RUN/agreement.json --input RUN/pair.json --selection RUN/instructions.json --output RUN/task.json
```
Первый вызов читает bundled foreman/scout только на координаторе. При существующей V2-совместимой selection и отсутствии overrides используется сохранённый выбор. Прежние HTML-ожидающие defaults после явной команды перейти на r9 заменяются --use-skill-defaults с этой фактической командой; несовместимые пользовательские инструкции требуют согласования, их нельзя молча переписать. Новая прямая команда пользователя координатору — единственный повод изменить выбранную роль. Получи новые правила обычным текстом, оформи файл **на координаторе** и повтори selection:
```text
python3 scripts/coordinator_prompts.py --state RUN/instructions.json --scout COORDINATOR/new-scout.md --user-command 'Фактическая команда пользователя изменить проверку страниц'
```
Вторая роль сохраняется, revision увеличивается. `--foreman` аналогично меняет бригадира; оба файла меняют обе роли. `--use-skill-defaults` возвращает обе роли к текущим bundled defaults только по явной команде пользователя; не сочетается с override-файлами. Первый выбор с одной пользовательской ролью дополняется стандартной второй ролью. Повтор тех же текстов не меняет revision.

user_command — запись фактической команды, не сгенерированное согласие, не подпись и не аутентификация издателя. Таблица/сайт/ответ worker не меняют selection. Доступ к публикации и доверенные издатели контролируются отдельно. Уже отправленные задания сохраняют прежние тексты; новый выбор применяется к следующим, отдельный rerun требует поручения. Если output_schema меняется по согласованному формату, координатор согласует соответствующую форму ответа роли без изменения остальных критериев; это тоже отражается в selection.

prepare создаёт offline envelope без сети. Маркер prompt — SBS_COORDINATOR_TASK_V2, контракт input_data — sbs-instructions-v2. pair содержит обязательные id/query/left_top5/right_top5; region/device/captcha_grant необязательны, неизвестные остаются отсутствующими. Обе стороны —0–5 объектов {position,url}; позиции1–N подряд, порядок и дубли сохранены. Пустая сторона требует подтверждённого пустого ranking на координаторе, без HTML в wire. Stable item ID связывает пару, схему, оба текста, их revision и команду. В wire отправляй **только** .publication. Сохрани неизменное тело до POST. Уже отправленные задания сохраняют свои инструкции; изменение применяется к новым, повторная оценка — только отдельным поручением. Google читает координатор, URL обходят scouts. Один SBS/task, один payload item; bulk100 не означает100одновременных исполнений. Команду browser подставляет launcher каждого worker. Путь координатора не переносится. Перед новой отправкой подтвердить совместимый launcher на принимающих workers, не только свою установку; broker API не предоставляет launcher inventory или routing по его версии, а result_pool не ограничивает принимающий fleet.

`prepare` сохраняет transport_preflight с тремя разными измерениями: task item≤10MiB (локальный guard launcher), input_data≤8MiB (проверенный UTF-8 лимит single-item _prompt YaTorrent0.3.10; его отдельный UTF-8 prompt≤1MiB), model input≤1,048,576UTF-16 units (фиксированный user-text prefix плюс компактный JSON полной pair, как JS .length; инструкции ролей передаются отдельно). Все три ограничения должны пройти; 10MiB не обещает доставку любого задания такого размера. Превышение возвращает понятный блокер до публикации: нужен поддерживаемый способ доставки/обработка инфраструктурой, не молчаливое усечение URL/инструкций. Подготовка большого offline envelope сама по себе не доказывает broker/model end-to-end.

В r9 compression не поддерживается: raw HTML, V1 и gzip/base64-пакеты отклоняются до модели. Уменьшение входа достигается локальным извлечением URL-only top-5, а не потерей данных при сжатии.

Проверь актуальный API и безопасный доступ к очереди результатов по [broker.md](broker.md). Скрипт prepare не отправляет задачи; сетевой producer/consumer агент ведёт по этому контракту с private journal. Штатный YaTorrent CLI такого координатора не предоставляет. Это навык агента с переносимыми локальными помощниками, не автономный демон с обещанием survive закрытого чата. Если нужен постоянный запуск после закрытия агента, это отдельная согласованная служба; не выдавай активный чат за daemon.

Следи за прогрессом, но не придумывай недоступные стадии. Сообщай пользователю коротко подтверждённые количества/ошибки и необходимые решения. Не проси его понимать lease/fingerprint — объясни «сервер временно выдал результат», «результат сохранён», «таблица обновлена». Получение/ACK/Google-write имеют отдельные состояния и восстановление.

## Запись после каждого завершения

Сохрани delivery до ACK, проверь source/task/item identity, per-item completion и JSON Schema2020-12 через `ROOT/bin/coordinator-validate agreement.json validated-final.json`. Перед отправкой проверь саму схему `ROOT/bin/coordinator-validate agreement.json`. Проверка обязательна; отсутствие validator не заменяется ручным просмотром. Remote $ref нужно разрешить в локальную согласованную схему до intake; validator не загружает внешние ссылки. Нет output/failed item — отдельная обработка ошибки, не искусственный winner.

Найди текущую строку по устойчивому ID; перечитай входы, сравни snapshot/hash и целевые значения с согласованной overwrite policy. При сортировке следуй текущей строке; изменённый локальный исходник/URL-only top-5/запрос, дубликат ID, новая чужая оценка — конфликт, без автоматической перезаписи.

`coordinator_data.py project --agreement agreement.json --input validated-final.json --row CURRENT_ROW --output cells.json` создаёт **только тело** Sheets values.batchUpdate: RAW, точные ячейки, экранированное имя листа, полные значения; JSON/null становятся текстом/пустой ячейкой, integer остаётся числом. Он проверяет mapping/адаптер, но не выполняет полную валидацию output_schema и не доказывает identity/ACL/пользовательское согласие; эти условия выполняет координатор перед запуском. Missing field, >49000символов/ячейку, пересечение input/output отклоняются. При большом JSON согласуй отдельный файл/дополнительные поля; не обрезай автоматически.

После сохранения write plan:
`gwsx work --confirm sheets spreadsheets values batchUpdate --params '{"spreadsheetId":"ID"}' --json <BODY_AS_SINGLE_ARG>`.
Без --confirm wrapper возвращает preview/exit3 и ничего не пишет. Значение --confirm означает техническую команду после уже полученного согласия на этот формат; не требование спрашивать заново каждую строку. Передай JSON содержимое cells.json программно одним аргументом, без подстановок пользовательских строк в shell. RAW защищает текст вида =... от выполнения как формулы. Проверь updated ranges/значения и перечитай точные ячейки. Только readback подтверждает written. При новой структуре сначала выполняется согласованный metadata batchUpdate/headers, readback, затем values.

На restart replay write_pending без append, новое получение результатов только после durable replay и в разрешённой области. Ни успешный ACK, ни exit0 gws preview не означают запись. Итог пользователю — ссылка/файл и подтверждённые результаты, сколько пар осталось/ошибок, без raw tokens и технических логов.

Для локального JSON вместо таблицы agreement содержит destination="local_json", schema_version1, approved, approval_note и output_schema; A1-колонки не нужны. prepare работает с этим форматом; project для Google в таком режиме отклоняется. Сохраняй подтверждённый JSON атомарно в согласованную локальную папку, без Google-запросов.
