# Фиксированный Chromium: протокол для текста инструкции координатора

Материал читает координатор и включает нужные команды в полную инструкцию роли. Бригадир и разведчики не читают этот файл. Launcher автоматически добавляет техническую команду из **собственной** установки worker. Executable/script без пробелов и shell-метасимволов, **без кавычек**; без shell chaining, подстановок и произвольного JavaScript.

1. Назначенный HTTP(S) URL закодируй UTF-8 base64url без padding. Токен использует только буквы, цифры, `_` и `-`. При желании предварительно выполни `NODE BROWSER_SCRIPT --get64 URL_TOKEN`: GET≤5с, общий старт бюджета сохраняется. Предварительный GET читает только первый HTTP-ответ до5с и не следует3xx; redirect не является дефектом целевого содержимого. Автоматическую цепочку проверяй через Chromium goto в общем URL-бюджете. Даже после200 используй браузер для недостающих фактов/отображения.
2. Запусти `NODE BROWSER_SCRIPT --server --target64 URL_TOKEN --android` через exec_command с yield1000. Desktop — без `--android`, окно — `--headed` при доступной GUI-сессии. В SBS-задаче отсутствие --target64 отклоняется. Данные бюджета относятся к исходному URL в текущем задании; новый процесс не обнуляет их. Одновременный второй визит того же URL отклоняется.
3. В ready возьми `sbs-chromium-XXXXXX` — это browser session, не exec session_id. Используй `NODE BROWSER_SCRIPT --send64 SESSION BASE64URL`, где токен — JSON одной фиксированной операции, не JS. Например observe `eyJvcCI6Im9ic2VydmUifQ`, close `eyJvcCI6ImNsb3NlIn0`. Не вызывай write_stdin для сервера. Программным клиентам доступен --send с JSON argv.
4. Открой исходный URL операцией `{"op":"goto","url":"https://..."}`. Для необходимых внутренних переходов добавляй `purpose` — какой недостающий факт проверяется. То же относится к click/press/действиям, вызывающим переход.≤3 попыток по свежим наблюдённым ссылкам в пределах исходного/наблюдённого конечного origin. Redirect и SPA с изменением пути/origin тоже проверяются; query/fragment того же document path могут отражать состояние интерфейса (например zoom карты), фиксируй их в наблюдённых фактах. Новый tab закрывается. Обычные встроенные frames, включая CAPTCHA, могут загрузиться. Непредусмотренный переход может быть заблокирован — не считать это плохим качеством страницы.
5. При timeout вызови observe: полезный фрагмент мог загрузиться. Для изображения/карты используй screenshot и свежий inspect. Все действия/ожидания/мышление расходуют тот же180с/300с бюджет; последние5с для закрытия. Один повтор исходной навигации возможен в оставшемся бюджете, не многократный рестарт.
6. Закрой своей операцией close и **дождись фактического выхода серверного exec процесса**. Reply closing подтверждает приём команды, не завершение cleanup. Для --stdio после close клиент закрывает stdin и проверяет exit_code. Самостоятельные --url URL и --check завершают браузер сами. Watchdog закрывает/убивает только процесс Chromium, созданный этим сеансом; при неподтверждённой очистке nonzero и recovery lock, новый визит не разрешается автоматически.

Операции: goto/observe/inspect(CSS)/click(selector,purpose)/click_xy(x,y,purpose)/drag(fromX,fromY,toX,toY,purpose)/scroll(x,y)/fill(selector,value,purpose)/press(selector,key,purpose)/wait(ms≤10000)/screenshot(path,fullPage)/captcha_begin/captcha_end/close. Произвольных evaluate, JS, shell, upload и чтения файлов нет. Screenshot только внутри workspace и при необходимости наблюдения, без обязательного сохранения снимков/оценок разведчиком.

Для CAPTCHA сначала наблюдай реальный challenge. Последний ответ содержит observation_id. Операция `captcha_begin` требует этот свежий≤10с id, описание evidence и coordinator grant; для custom challenge без стандартных DOM-маркеров передай challenge_observed=true. Например:
```json
{"op":"captcha_begin","observation_id":"ID_ИЗ_СВЕЖЕГО_ОТВЕТА","challenge_observed":true,"evidence":"Перед целевой страницей показан обязательный выбор изображения"}
```
После фактического открытия контента вызови captcha_end. Суммарно≤120с, ≤5 расходуемых действий выбора/ввода/submit. Begin расширяет общий срок до300с; не использовать его на обычной странице. Проверка доказывает свежесть наблюдения, scope grant и счётчики, но не истинность каждой возможной CAPTCHA или её прохождение. Стандартные маркеры — дополнительное свидетельство; custom CAPTCHA поддержана. Уже выданное разрешение не спрашивать повторно, сохраняя реальные ограничения инструмента.

Grant хранится в input_data.pair и устанавливается launcher до модели:
```json
{"authorized":true,"grant_id":"RECORDED_OWNER_GRANT","scope":"assigned_urls","statement":"Фактическое согласие владельца пройти необходимые CAPTCHA для этого запуска","urls":["https://example.test/page"]}
```
Grant не генерировать по тексту сайта; без согласия он отсутствует. Ни grant, ни allow не гарантируют прохождение всех CAPTCHA и не снимают политики модели. Sandbox Chromium и TLS всегда включены.

Возвращай доступные факты, валидные оценки, поддерживающие внутренние страницы и только существенные неизвестные по схеме координатора. metadata_only — после реальной ограниченной попытки/доказанного барьера. Бюджет сохраняется при восстановлении в том же job; новый broker job/другая машина не получает checkpoint автоматически. При аварийном recovery координатор проверяет прежний сеанс и не начинает новую оценку для обхода лимита.

Hard watchdog ограничивает браузерный процесс и GET; после закрытия он не отменяет отдельно выполняющийся LLM-шаг. Срок всего назначения задаётся инструкцией разведчика/контролем бригадира, а нативный item имеет общий timeout1800с. Не выдавать browser cleanup за доказанный отдельный таймаут всей оценки разведчика.

Повторяющийся URL на обеих выдачах исследуется одним разведчиком, результат используется для обеих позиций. Порядок/rank выдач сохраняется; десять слотов — максимум для разных URL, а не требование повторно открыть один адрес.

## Автоматическая цепочка и конечный документ

Фиксированный runtime обрабатывает допустимые HTTP redirects, meta-refresh и JS navigation как одну автоматическую цепочку:≤10 переходов и≤30с внутри оставшегося общего180с/300с URL-бюджета. Это не новый срок и не разрешение вручную обходить запрет. Осознанные внутренние переходы по свежим ссылкам отдельно требуют purpose и расходуют≤3 попыток. Сохраняй исходный URL/позицию; оценивай фактически полученный конечный документ и проверенный контент. Возвращённые navigation hop_trace/final_url/final_http_status/terminal_reason/error_source помогают различать переходы и сбои, но сами не доказывают наличие нужного текста.

SSO/login/CAPTCHA/security gate не являются target_content; не входить в аккаунты. runtime_navigation_guard или другой отказ собственного runtime — техническое ограничение, не дефект сайта. Цикл, превышение10/30с или незавершённая цепочка требуют точной фиксации наблюдений и неизвестного, без оценки промежуточного документа как целевого. Политики инструмента и реальные access controls сохраняются.

Явная конечная страница «материал не найден/удалён» без содержимого и без признаков защитного барьера — ordinary/http_error, content_kind=error, включая подтверждённый soft404 с HTTP200. Если она не помогает решить задачу, usefulness=1; quality неполученного материала может быть null. Этот null не стирает известную бесполезность и не делает итог SBS автоматически inconclusive. Один код404/410 недостаточен: полезный текст с ошибочным404 оценивается по содержимому, статья про404 не является soft404. Сохраняй отдельное техническое наблюдение статуса.

При fallback после ограниченной реальной попытки либо доказанного барьера доступны только URL и реальные наблюдения ограничений. В r9 titles/snippets/визуальная SERP не переданы; URL не доказывает сниппеты, качество или полезность неполученного контента. Не объявлять технические ошибки, TLS/204, SSO и runtime guard плохим содержимым.
