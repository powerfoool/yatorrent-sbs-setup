# Broker: публикация, получение и восстановление

YaTorrent desktop — worker, а не producer: стандартный CLI не имеет команды SBS-coordinator. Координатор взаимодействует с API брокера отдельно. Пакет даёт инструкции и offline helpers; он не патчит нативный протокол и не отправляет реальные задания при setup/verify. endpoint/credentials берутся из внешнего AIM2 владельца локально, не передаются бригадирам или в публичный ZIP. HTTP разрешён только при явном allow_http профиля; TLS не отключать, Authorization не отправлять на другой хост при redirect.

## Проверка API на целевой среде

Перед сетевой работой прочитай актуальный /openapi.json или первичную документацию данного сервера. Снимок split v2:
- POST /v1/tasks: `{item_id,task_type:"codex",payload:[{id,prompt,input_data,output_schema}]}`. Одна пара — один item в payload и один broker task. Не добавлять model/schema_version в PromptItem; модель выбирает worker. Сохрани неизменное тело и ID до POST. Успех: status=published с совпавшим item_id и task_id. Не приравнивать conflict/pending/HTTP200 к публикации.
- GET /v1/results?request_id=...: ответ `{request_id,result:null|ResultLease}`. Это захват доставки, **не read-only status**. Нет task_id/task_type/publisher фильтра. Старый API имел иной ACK endpoint; не смешивать dialects.
- result lease: task_id/task_type/status/result_id/result/error/delivery_id/delivery_token/delivery_status/lease_until. В status=succeeded результат ещё может содержать failed item. Ожидаемый item: `{id,status:"completed",output:...}`; провал `{id,status:"failed",error:...}`. Проверяй каждого, его ID и согласованную JSON Schema, не только внешний status.
- POST /v1/results/ack: `{result_id,delivery_id,delivery_token}` без operation. Успех: status=acked с совпавшим result_id. Не печатай токены доставки.

Проверенный снимок не доказывает текущую доступность/права, срок дедупликации или exactly-once сервера. При несовпадении схемы остановить эту сетевую стадию; не угадывать дополнительные поля.

## Общая очередь и мониторинг

До первого GET/results проверь изоляцию очереди или согласованный способ потребления/маршрутизации всей очереди. Объясни пользователю без API-терминов: «Получение может забрать результаты других задач. Рекомендую отдельную очередь для этого запуска; другой вариант — договориться, кто сохраняет и распределяет все результаты». Не ACK чужие результаты ради очистки; при неожиданной чужой доставке сохрани её приватно и останови новые claims до разрешённого маршрута. Без ACK она всё равно временно скрыта lease.

Этот API не предоставляет per-task execution status/heartbeat. Координатор сообщает подтверждённые состояния: подготовлено, отправлено, результат получен, сохранён локально, записан в таблицу, ошибка. Отсутствие результата означает ожидание, а не доказательство работы/зависания. Чтение локальных метрик своей машины — дополнительная диагностика, не обзор других workers. Если недоступен безопасный result consumer, настройка инфраструктуры может быть готова, а запуск координатора — заблокирован; объясни конкретный недостающий доступ.

## Журнал без базы данных

Координатор создаёт private run directory0700 и атомарные JSON файлы0600: согласованный формат+schema hash, снимок входов/устойчивые IDs, planned immutable publications, publication receipts/task_id, текущий result request_id, inbox deliveries, processed outcomes, ack receipts, pending cell writes и readback receipts. Один активный координатор на run; исключи одновременные записи одного журнала. Credentials/lease tokens не выводить и не переносить в публичные артефакты.

На restart сначала replay локального журнала. Сетевые повторы используют неизменные item_id/тела. Изменение входа/рубрики/схемы — отдельный запуск, не новый текст под старым ID. До GET сохрани новый request_id; при потерянном ответе повтори его. После успешно сохранённого ответа (включая null) retire этот request_id и для нового poll создай следующий. Иначе можно вечно получать cached null.

Доставка сохраняется durable **до ACK** вместе с task/item/source binding. Нельзя ACK ещё не сохранённый результат. После локального ingestion ACK может предшествовать Google-записи, чтобы не держать lease при недоступном Google; сохраняй разные ingested/acked/write_pending/written. При конфликте/истекшем lease не выдавай ACK за успешный: получи новую разрешённую доставку того же result, сохрани новый delivery ID/token. После потери ответа ACK повторяется точное прежнее тело; чужие delivery tokens не подменять. Не сбрасывай журнал после ошибок.

Google write восстанавливается отдельно: найти текущую строку по устойчивому ID, перечитать query/оба HTML, сравнить hash входа, существующие целевые ячейки, записать детерминированные значения RAW и перечитать точные диапазоны. Если вход/колонки/чужая оценка изменились, отметить конфликт и не перезаписывать молча. ACK не означает written; output готов только после подтверждённого readback. Формат пользовательских ошибок также согласовать, не ставить выдуманный winner.

## Предел проверки установки

`delivery_ready=true` относится только к local_worker_only. broker_end_to_end_verified=false и parallel_jobs_verified=false остаются до реального разрешённого теста назначения/исполнения/получения/ACK. Worker outbox acknowledged означает worker→broker, не ACK конечного получателя. Настроенные4jobs/11agents не доказывают нагрузку. Тесты пакета используют локальные fixtures и не читают общую очередь, не отправляют jobs и не изменяют Sheets.
